## 3. 二期规则与实现边界

### 3.1 最小业务流程

1. 按已有业务版本、用户和模型校验配置存在、启用、quota 通过，并遵守模型自身可用性规则。部门有 Key 不会给新人授权。
2. 准备首次真正对外提交时，后端读取用户当前有效主部门和祖先链，按 `providerCode` 从近到远找生效映射。
3. 在真实外部尝试对应的持久化记录先写 `appKeyMappingId` 和 `departmentIdSnapshot`，成功后才发请求。组织查询或绑定失败则不提交，不回退旧个人 Key。
4. 同一外部任务的轮询、查询、重试及需要凭据的下载/回调处理按固定 ID 取原 Key，不再解析人的现部门；历史映射停用仍可读。
5. 用户重新生成若产生新外部任务，则重新校验权限/额度并解析当前部门。内部一主多子、多 provider 或同步模型均按真实执行粒度适配，不凭 PRD 造表。

### 3.2 映射与部门快照

逻辑字段沿用 PRD：稳定 `id`、可读 `mappingCode`、`providerCode`、`departmentId`、`appKey`、生效状态及必要审计时间。优先复用既有持久化规范，数字 ID 为建议，数据库引擎与类型未定。

- 同模型同部门最多一条当前生效映射，允许历史版本；Key 本身不唯一。多个部门共 Key 时分别有独立映射 ID。
- 子部门优先，未配置则继承最近有效祖先；无效链、环、多个 active、主部门不明均明确失败，不跨兄弟部门或用 Key 猜归属。
- 已引用映射的凭据及归属不可原地改写，不物理删除；换 Key 新建版本并受控切换。active 唯一性及并发切换须在实际引擎验证，不能只靠“平时由研发改”保证。
- `departmentIdSnapshot` 是首次外部尝试时用户实际部门，可能是小组；映射上的部门可能是其上级。共 Key 不等于同部门；快照用于核对，不自动构成财务分账规则。
- 由授权研发低频受控维护，不建业务 Key 管理页；任务只存引用，不重复明文凭据。优先遵循已有安全存储规范，不新增独立凭据平台作为前置条件。

### 3.3 旧任务兼容与切换

新任务强制绑定；旧任务临时走原用户配置 Key 读取。判据必须能区分“切换前已对外尝试”与“仅在内部排队”；空映射 ID 或内部任务创建时间不能单独证明是合法旧任务。新链路漏写应失败。

已排队但切换后首次对外提交的任务要满足新规则；可选统一升级消费者后恢复队列，或受控排空/暂停切换，须按现有架构选择并验收。任何方案都不能将新调用悄悄退回旧个人 Key。

不做全量旧任务回填。旧路径依赖原用户配置仍存在、Key 未改写且服务商仍接受；删除记录、改过旧值或 Key 撤销的极少数异常按产品接受的人工处理机制执行。保留历史行不能保证已撤销凭据可用。R06/R10 未核实前，不承诺所有旧任务自动恢复，不提前删旧列。

### 3.4 管理接口与批量 quota

尚无真实接口契约，本文不规定接口名、路径、响应字段名或物理表。研发应基于原服务确认以下输入输出保证：

| 能力 | 必须保证的业务行为 | 待真实契约确认 |
| --- | --- | --- |
| 用户配置列表/详情 | 保留用户、模型、quota、启停、时间；派生当前部门；响应无 Key | 部门只读字段、分页和排序实现、导出与错误字段白名单 |
| 新增/编辑/删除 | 新人仍人工授权；不接收可写 Key；主标识沿用一期只读规则 | 旧字段的拒绝/忽略兼容策略、删除与旧任务依赖、审计 |
| 部门过滤 | 正式部门 ID，默认仅直属，含下级则所有子孙；后端全量过滤 | 组织服务、主部门、缓存时效与批量查询性能 |
| 批量 quota | 当前业务版本+部门范围+必选模型；命中启用及停用的已有配置；只整包覆盖 quota | 预览/执行重新匹配、实际修改数、失败或部分成功语义、并发与审计 |
| 旧按 Key 批量入口 | 二期关闭/拒绝旧命中路径，不靠隐藏按钮 | 旧客户端调用者清单及撤销顺序 |
| 权限 | 美工/运营数据与操作边界独立；后端鉴权；授权业务代表可跨部门看人员/quota | 实际菜单/按钮/接口权限键；不另建部门行级权限系统 |

业务端去 Key 覆盖页面数据、DOM、请求/响应、Network、导出、日志、错误、审计及任务查询，不能仅删除一列表格。实际部门只能从权威组织源读取，客户端不能通过提交部门或业务版本绕过鉴权。

预览数、执行命中数和 quota 实际发生变更数不能混用。执行时组织已变化则按最新关系匹配并反馈；范围显著变化可要求重新确认。复用已有事务与审计能力，不默认建设预览 token、第二套组织系统或自动补偿平台。

### 7.4 生产实施的最小顺序

1. 在企业真实项目确认存储、组织解析及外部任务粒度，验证映射初始化覆盖和 active 唯一约束。
2. 完成新任务按当前部门解析、先落绑定后提交、旧任务按固定 ID 读取及上线前旧任务兼容。
3. 完成业务 API 去 Key、旧写入/按 Key 批量入口封闭及后端权限；再交付两版管理页的组织展示/筛选和部门批量 quota。
4. 以真实用例验证调岗、超时、换映射、共享 Key、启停授权、数据隔离、无 Key 泄露后发布；两项业务目标尽量同期完成。
5. 确认旧任务及其他依赖结束后清理旧物理字段与临时路径。不因解析失败恢复旧个人 Key 作为新任务回退。

判断完成时仍以四条底线为准：新任务费用归属正确、已有外部任务使用原凭据、业务端取不到 Key、无用户授权不会放行；另需交付按当前组织小组批量更新已有配置 quota 的能力。
