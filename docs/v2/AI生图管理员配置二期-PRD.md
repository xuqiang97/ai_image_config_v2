# AI 生图管理员配置二期 PRD

> **版本：** V1.2，产品评审版
>
> **日期：** 2026-10-22
>
> **适用范围：** 美工管理员配置、运营管理员配置及相关生图任务
>
> **配套原型：** [打开轻量 HTML 原型](../../index.html)

本 PRD 与配套 HTML 原型共同说明本期最终产品方案。人员和部门关联、任务凭据规则、页面行为及验收标准以本文为准，具体实现由研发确定。

原型沿用一期布局与蓝色主题，演示列表筛选、单人配置、部门批量额度更新。所有人员、部门及额度均为虚构示例；修改只在当前打开的页面中生效，刷新恢复。原型不演示真实生图、计费或后台凭据匹配。

## 0. 需求概要与核心原则

**部门决定新任务使用的生图凭据，用户配置决定生图资格与额度，已提交任务继续使用发起时的凭据。**

| 事项 | 最终方案 |
|---|---|
| 人员与部门 | 生图配置的 `userId` 对应 `rb_admin.ID`，所属部门取 `rb_admin.DepartmentID`；兼管部门不改变个人归属 |
| 部门与凭据 | 按模型分别配置部门凭据；本部门未配置时，逐级使用最近上级部门的有效配置 |
| 人员调岗 | 新任务实际发起时实时查询当前部门；已提交任务继续使用首次提交时绑定的部门和凭据 |
| 个人授权与额度 | 保留用户级配置、quota 和启停；部门变更不自动开通、启用或重置个人额度 |
| 部门或凭据异常 | 允许先保存人员额度配置；实际生图时若无法获取有效部门或凭据，任务判失败、记录原因并进入「已完成」 |
| 管理页面 | 移除 appKey 的展示、查询与维护；增加当前所属部门展示和筛选 |
| 批量更新 | 按当前页面、所选部门、是否含下级及模型，整份覆盖已有配置的 quota |
| 修改范围 | 包含启用和停用配置，保留启停状态；不为未配置的员工自动新增配置 |
| 页面边界 | 美工、运营保持独立入口和数据范围；原型侧栏仅用于对照演示 |

优先保证部门费用归属正确、已提交任务可继续查询，以及业务端不泄露凭据；部门批量额度功能目标同期完成。

## 1. 背景及目标

### 1.1 现状与问题

根据产品提供的现状，一期在个人模型配置中维护 appKey，人员调岗后需要人工更新，容易继续使用原部门的凭据并产生费用错配。多个小组可能共用同一凭据，原来的按 appKey 批量修改无法准确区分小组。业务管理页面还会暴露完整凭据。

### 1.2 本期目标

- 人员调岗后，新任务使用其当前部门应归属的生图凭据，减少人工维护。
- 保留现有个人生图资格、额度和启停管理，允许同部门不同人使用不同额度。
- 可按正式组织中的部门或小组，准确批量更新已有用户配置。
- 已提交任务继续使用原凭据查询结果，并可核对实际发起部门。
- 业务管理员只维护人员和额度，部门凭据由授权研发低频维护。

## 2. 本期范围

### 2.1 包含

- 复用公司现有员工及部门组织关系，获取当前有效部门。
- 按模型与部门维护凭据归属，并支持向上继承。
- 新任务按当前部门取用凭据；已提交任务固定原凭据及发起时部门。
- 美工、运营管理员页面去除 appKey，增加部门列、部门筛选及部门批量额度操作。
- 保留一期个人配置、quota 校验、启停、权限及数据边界。
- 保证上线前已提交任务在过渡期内能够继续按原方式处理。

### 2.2 交付边界

复用现有组织数据和生图任务流程；业务管理员维护人员配置及额度，授权研发维护部门凭据。个人生图资格继续由用户级配置控制，已停用模型仅保留历史配置及任务处理能力。

本地 HTML 仅为页面交互评审辅助，使用模拟数据展示管理员配置操作。任务规则通过评审说明与 PRD 表达，真实生图流程由研发实现后验收。

### 2.3 用户与部门关联

- 生图用户配置中的 `userId` 对应 `rb_admin.ID`，不是员工工号。
- 通过 `userId` 查询员工记录，取得 `rb_admin.DepartmentID`，再关联 `rb_department.ID` 获取部门详情；上级部门关系使用 `rb_department.ParentID`。
- 人员展示、部门筛选、批量配置范围及新任务凭据匹配，统一以员工的 `DepartmentID` 为所属部门依据。
- `rb_department.LeaderID` 表示部门负责人，不用于判断员工所属部门。兼管其他部门不会自动将该员工纳入那些部门的筛选或批量范围。
- 现有组织系统负责维护员工归属。本期以查询时的组织记录为准，不新增组织同步机制或同步时效指标。
- 部门名称可变更，筛选和匹配仍应稳定指向同一个正式部门。
- 初始部门数量不限制后续新增部门；特殊部门也可独立配置凭据。

## 3. 部门生图凭据规则

### 3.1 配置与维护

- 按生图模型分别配置。同模型、同部门同时只能有一个有效配置。
- 多个部门允许共用同一凭据，不能因为凭据相同就认定人员属于同一部门。
- 本期涉及 LinkFox、自研以及已停用的阿里绘蛙历史配置；保留历史数据不等于恢复模型的新任务。
- 部门凭据由授权研发受控维护并保留变更记录，业务管理员无查看和维护入口。
- 凭据变更应保留已有任务需要的原配置；不得覆盖或删除仍被任务使用的历史凭据。

### 3.2 新任务匹配

1. 实际发起新任务时，按第 2.3 节关联实时查询人员当前部门，以本次查询结果及使用的生图模型为准。
2. 本部门有有效配置时优先使用；没有则沿组织父级逐级向上，使用最近的有效配置。
3. 不跨兄弟部门寻找，不通过相同凭据反推人员所属部门。
4. 无有效部门、逐级向上仍找不到有效配置、配置冲突或凭据不可用时，按第 5.5 节结束任务；不得回退为旧个人凭据继续调用。

例如：美工一组、美工二组均未单独配置时，可以使用创意设计部的凭据；美工一组配置独立凭据后，该组优先使用自己的配置。IT 部可以配置与销售部相同的凭据，其下属产品组、测试组按相同规则继承。

### 3.3 组织及凭据变更

- 部门改名不影响对应人员的新任务匹配。
- 员工的 `rb_admin.DepartmentID` 更新后，后续新任务按实时查询到的新部门匹配有效凭据；未更新时按当时表中的部门处理。
- 更换或停用旧部门配置仅影响后续新任务，已有任务继续使用发起时的原凭据。
- 若服务商已彻底撤销原凭据，系统应明确反馈异常并支持人工处理，不能承诺仍可取回结果。

## 4. 用户级配置与生图资格

1. 在当前业务页面范围内，同一用户、同一模型只保留一条配置。
2. 没有配置、配置停用或额度不足，均按现有规则拒绝生图。
3. 部门存在有效凭据不等于人员已获得生图授权；新人仍需管理员手动新增配置。
4. 调岗不自动改变用户的启停状态和个性化 quota。
5. 同部门不同人可以有不同 quota，仍可单独维护。
6. 本期不改变剩余额度、用量、扣减和重置的既有口径。
7. 新增人员额度配置不以部门或部门生图凭据齐全为保存前提；相关异常在实际生图时按第 5.5 节处理。

## 5. 新任务与已提交任务

### 5.1 新任务

先检查个人生图资格和额度，在首次真正提交外部生图请求时，通过 `userId` 实时查询 `rb_admin.DepartmentID`，再查询部门及其上级部门的有效凭据。仅进入内部排队、尚未对外提交的任务，在实际提交时执行这次查询。

本次查到的部门即为任务发起时的实际所属部门。组织归属的更新及更新时效由现有组织系统负责；本期按查询结果处理。

### 5.2 已提交任务

任务首次提交时固定实际所属部门及使用的凭据，作为该任务的快照。结果查询、轮询及同一外部任务的重试，始终沿用快照中的原凭据；人员调岗、部门配置调整或旧配置停用，不应导致其改用另一凭据。

任务需保留“发起时实际所属部门”和“使用哪个部门的凭据”的关联，便于费用使用核对；多个部门共用凭据时，两者仍应区分。具体记录方式由研发确定。

### 5.3 重试与重新生成

- 同一外部任务的失败重试或超时后继续查询，沿用原凭据，避免重复生成和重复计费。
- 用户重新发起生成、实际创建新的外部任务时，重新检查资格、额度和当前部门。
- 一个内部任务产生多个实际外部任务时，每个外部任务均应符合以上规则。

### 5.4 历史任务过渡

- 上线前已对外提交的任务，可在过渡期内继续按原方式查询，无需全量回填。
- 上线后首次对外提交的任务必须遵循新规则，不能因缺少记录而误走历史路径。
- 历史任务结束、相关依赖清理完成前，应保留查询所需的原凭据与关联信息；业务页面可先移除相关入口。
- 极少量历史异常允许人工处理。若原配置已删除或凭据已撤销，需明确异常，不宣称一定可恢复。

### 5.5 部门与凭据异常

实际生图时，若未获取到有效部门，或按本部门及上级部门查找规则仍未匹配到有效生图凭据，直接将任务判为失败，记录具体错误原因并结束处理。

| 异常 | 错误原因示例 |
|---|---|
| 未获取到有效所属部门 | 未获取到用户所属部门 |
| 本部门及上级部门均无对应模型的有效凭据 | 所属部门及上级部门未配置 LinkFox 生图凭据（其他模型使用对应名称） |
| 部门配置冲突或凭据不可用 | 部门生图配置异常 / 生图凭据不可用 |

失败任务进入「已完成」，结果明确标记为失败，并可查看错误原因。「已完成」表示任务处理结束，不代表生成成功；任务不继续停留在处理中。错误信息仅描述原因，不包含实际凭据。

## 6. 美工与运营管理员页面

### 6.1 独立入口

- 美工、运营保持两个独立页面和各自配置范围。
- 筛选、分页、查看、编辑、批量更新均限制在当前业务页面内。
- 原型左侧切换仅用于评审；切换后恢复该页面的默认查询状态。

### 6.2 列表与查询

| 项目 | 规则 |
|---|---|
| 列表信息 | ID、用户ID、用户名、当前所属部门、生图模型、quota、状态、更新时间、操作 |
| 移除项 | appKey 列、查询条件、查看、复制及编辑入口 |
| 当前所属部门 | 显示当前正式组织归属；必要时显示父级名称便于区分；缺失时显示“未匹配部门” |
| 部门筛选 | 通过可搜索的组织树选择正式部门；未选择表示全部部门 |
| 包含下级部门 | 默认关闭，仅查直属人员；开启后包含该部门及所有下级人员 |
| 其他条件 | 保留用户ID、完整用户名、生图模型和状态筛选 |
| 排序与分页 | 更新时间倒序，同时间按 ID 倒序；默认 20 条，可选 20/50/100 条 |

### 6.3 新增、查看、编辑、删除

| 操作 | 规则 |
|---|---|
| 新增 | 填写用户ID、用户名、模型及 quota，默认启用；不填写生图凭据 |
| 用户ID | 填写生图用户ID，即 `rb_admin.ID`，不是员工工号 |
| 部门信息 | 按第 2.3 节关联获取，只读；新增填写用户ID后展示对应部门，缺失时显示“未匹配部门” |
| 查看 | 展示个人配置、当前部门、quota、启停及时间信息 |
| 编辑 | 用户ID、用户名、模型及部门只读；可修改 quota 与启停状态 |
| 删除 | 二次确认后仅删除当前用户在当前页面的该模型配置，其他配置不变 |

部门缺失或未配置生图凭据时，允许先保存人员额度配置。保存过程不额外增加部门凭据预检、异常告警或阻断流程；部门字段保留正常的只读展示。实际生图时发现异常，按第 5.5 节判失败并结束任务。

### 6.4 按部门批量更新 quota

入口名称为【按部门批量更新 quota】，替换原按 appKey 批量更新入口。

**操作流程：选择范围 → 填写 quota → 核对确认 → 查看执行结果。**

| 内容 | 规则 |
|---|---|
| 所属部门 | 必选，可搜索正式组织中的部门或小组 |
| 包含下级部门 | 默认关闭；开启后包含所有下级组织 |
| 生图模型 | 必选，只修改该模型 |
| quota | 必填，支持结构化填写和 JSON 直填，整份覆盖 |
| 命中预览 | 显示预计命中已有配置数，明确包含停用配置；改变范围后重新预览 |
| 确认内容 | 当前业务页面、部门、是否含下级、模型、预计条数、完整 quota 及覆盖提醒 |
| 成功结果 | 显示实际匹配和实际修改条数；原额度相同的记录不计为值已修改 |
| 无命中 | 提示“未命中任何记录”，保留输入，调整条件后可重试 |

批量操作仅整份覆盖已存在配置的 quota，不做字段合并。原 quota 中未在本次填写的字段会被移除。包括启用、停用配置，但不改变启停状态，不修改人员归属，也不自动新增未配置员工。

执行以当时最新的组织关系和权限为准。若结果与预览不同，应反馈真实条数；范围变化较大时重新确认。失败保留输入并明确提示，不能把失败或部分成功显示为全部成功；研发应在实现评审中说明最终失败处理方式。

例如：美工一组和美工二组共用同一凭据，选择美工一组时只修改该组。IT 部与销售部共用凭据，选择销售部也不会同时修改 IT 部。

### 6.5 quota 输入与校验

- quota 是非空 JSON 对象，至少包含一个字段。
- key 以字母或下划线开头，仅包含字母、数字、下划线，不允许重复。
- value 为非负整数，允许 0；不接受负数、小数、字符串等值，不新增业务额度上限。
- 两种输入方式使用相同校验；切换、保存、回显均不能丢失字段或静默改变数字。
- 固定展示顺序：`total → scene → closeUpWhite → closeUp → sellPoint → aplus`，其他字段随后展示。

### 6.6 交互与反馈

- 查询、保存、删除和批量提交提供处理状态，避免重复操作。
- 校验失败或操作失败时保留输入，提供可理解的错误提示。
- 抽屉支持关闭按钮、取消、遮罩关闭和 Esc；存在确认框时 Esc 先关闭确认框，并恢复到原操作位置。
- 沿用一期蓝色主题、侧栏、筛选卡片、表格、右侧抽屉和二次确认样式。
- 原型只使用模拟数据演示成功、无匹配、输入错误和部门缺失；真实网络故障、组织变动及生图链路由研发实现后验收。

## 7. 权限与信息安全

- 仅已授权管理员可查看和维护配置；保留原菜单、按钮和服务端权限校验。
- 允许已授权的部门代表跨部门核对人员与额度，本期不新增按部门的数据隔离规则。
- appKey 不出现在业务页面、页面数据、业务接口、导出、普通日志和错误提示中；旧写入入口同步关闭。
- 部门凭据仅由授权研发维护；业务人员不获得读取权限。
- 配置、启停及批量额度修改保留必要操作记录：谁、何时、修改了什么范围、结果如何。

## 8. 上线验收边界

- 上线前确认使用中的模型和部门均能正确匹配，缺失项有明确处理结论。
- 验证调岗后的新任务归属，以及调岗前任务的结果查询、重试和异常反馈。
- 验证页面操作、权限及凭据移除，特别是批量更新范围与真实结果数量。
- 过渡和回退都必须保持已有任务的原凭据关联，不能重新引入跨部门使用错误凭据的问题。
- 上线顺序、兼容期限、监测及回退实施由研发安排；产品按上述行为和下列用例验收。

## 9. 核心验收标准

| 编号 | 前提与操作 | 可观察的结果 |
|---|---|---|
| A01 | 已授权用户的 `rb_admin.DepartmentID` 从 A 部更新为 B 部后，实际发起新任务 | 本次查询取得 B 部，新任务使用 B 部或其最近有效上级部门的对应模型凭据 |
| A02 | A 部发起的任务尚未完成，用户调到 B 部后查询结果 | 继续使用原凭据，调岗不影响查询 |
| A03 | 小组没有独立配置，提交新任务 | 使用最近一个有效上级部门配置 |
| A04 | 小组已有独立配置，提交新任务 | 优先使用小组配置 |
| A05 | 两个部门共用同一凭据，分别创建任务 | 均可生成，仍能区分各自实际发起部门 |
| A06 | IT 部借用销售部凭据，其子组提交任务 | 继承正确；未获用户授权者仍不可生图 |
| A07 | 用户配置不存在或已停用，尝试生图 | 拒绝提交，不因部门有配置而自动授权 |
| A08 | 用户额度不足，尝试生图 | 按现有额度规则拒绝 |
