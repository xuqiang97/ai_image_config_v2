## 需求概述

一期在个人模型配置中维护 appKey，人员调岗后需要逐人调整，容易产生费用归属错误；多个小组共用凭据时，按 appKey 批量修改也无法准确区分小组。

本期覆盖美工、运营管理员配置、相关生图任务及 LinkFox 词库查询：**将 appKey 从个人配置中拆出，按部门统一管理；新任务和词库实时查询按用户当前部门获取凭据，已提交任务的结果查询固定使用提交时的凭据。个人配置继续负责生图授权和额度。**

| 本期改动 | 具体做什么 | 解决的业务问题 |
|---|---|---|
| 1. 新增部门级 appKey 映射表 | 美工、运营分别建表、复用结构，各自在业务内建立“部门＋模型 → appKey”关系，支持上级继承及多个部门共用凭据，由研发按清单初始化和维护。 | 集中维护部门凭据，减少逐人配置 appKey，为新任务和词库查询提供部门凭据来源。 |
| 2. 增加任务级凭据引用 | 首次对外提交前保存 appKeyMappingId 和实际发起部门快照 departmentIdSnapshot；凭据归属部门通过映射记录获取，后续结果查询沿用原凭据。 | 避免调岗、换 key 后旧任务查不到结果，保留费用归属依据。 |
| 3. 调整现有个人配置表 | 保留用户、模型、quota、启停，增加创建人、更新人及逻辑删除；保留 appKey、appSecret 字段，全部依赖切换后 appKey 置为 NULL，appSecret 保持现状。 | 明确个人配置职责，保留个性化额度，支持误操作排查。 |
| 4. 改造批量额度更新逻辑 | 从按 appKey 更新改为按“部门＋模型”更新已有人员配置，整份覆盖 quota，保留启停状态。 | 共用 appKey 的多个小组可以分别调整额度。 |
| 5. LinkFox 词库查询改用部门凭据 | 美工、运营五类入口的词库候选列表和名称回显，改用用户当前部门的 LinkFox 凭据；词库 ID 保存及异常处理沿用既有需求。 | 解除词库查询对个人 appKey 的依赖，保持调岗后候选列表、名称回显及原 ID 处理一致。 |
| 6. 对话生图对接与本系统切换 | 新表及数据就绪后，由对话生图团队自行完成接入和历史兼容；确认依赖适配后切换本系统配置流程及词库查询，全部依赖退出后再将个人 appKey 置为 NULL。 | 避免切换期间新增配置、词库查询、其他项目或历史任务受影响。 |

以上六项均纳入本期交付，后端规则按相同顺序展开；具体任务表适配及接口实现由研发结合现有实现确定。

## 前端改动与原型

美工、运营保持两个独立管理页面，移除 appKey 相关入口，配置用户改为组织树查询，批量更新改为按部门及必选模型执行。工号查询、个人配置及 quota 编辑沿用现有功能，具体页面、字段文案和交互见 [HTML 原型](https://xuqiang97.github.io/ai_image_config_v2/)，数据规则和验收以本文为准。

人员选择复用[运营已完成生图页](https://web.zhcxkj.com/SMS/#/PMS/PMS_SUB/AiImageOperation/AICompletedRawImage)的创建人控件交互，部门选择复用[用户列表页](https://web.zhcxkj.com/SMS/#/SMS/SMS_SUB/AuthorityManage/UserList)；本期管理范围按第 3 节执行。

原型使用虚构数据，不连接真实接口，刷新后恢复；顶部【本期前端改动】仅供评审。后端能力须实现后验收。顶部线上链接对应已发布版本，本地修改发布后才会同步。

## 后端改动

### 1. 新增部门级 appKey 映射表

美工、运营分别新增部门级映射表，与现有个人配置表保持相同的业务划分。两张部门表复用字段、索引及维护规则，数据独立，不自动同步凭据或启停状态。

| 业务 | 现有个人配置表 | 新增部门凭据表 |
|---|---|---|
| 美工版 | `ai_image_gen_model_config` | `ai_image_gen_department_model_config` |
| 运营版 | `ai_image_operation_model_config` | `ai_image_operation_department_model_config` |

本系统新任务按固定业务选择个人配置表和部门凭据表，完整提交流程见第 2 节；对话生图对接见第 6 节。两业务不互相兜底。

部门归属统一通过用户配置的 `userId = rb_admin.ID` 取得 `rb_admin.DepartmentID`，再关联 `rb_department.ID`；上级关系使用 `rb_department.ParentID`。用户ID不是工号，`rb_department.LeaderID` 表示负责人，兼管部门不改变员工个人归属。

按部门选人、批量额度更新、新任务及 LinkFox 词库查询的凭据匹配均使用上述组织数据，个人配置不另存部门归属。部门改名不改变其匹配身份；新增部门、层级及人员归属变化后，下次读取按最新记录处理，时效沿用现有组织系统。

已配置凭据的上级部门 ID 不变、用户所在小组仍在其下级范围内，且沿途下级部门对该模型均未配置或仅有停用记录时，小组新增、改名、拆分合并或下级层级调整均继续沿最新组织关系继承该上级凭据，无需逐组维护 appKey 映射。启用配置异常时按第 2 节报错，不跳过异常继续继承。仅部门名称变化、ID 不变时，已有映射也无需调整。

- 每张业务表内按生图模型分别配置，同模型、同部门同时只能有一个有效配置；两个业务可分别为同一部门、同一模型配置凭据。上级已配置时，下级仍可为同一模型单独配置凭据；查询优先使用下级自己的有效配置，未配置或停用时才逐级向上继承。
- 多个部门允许共用同一凭据，不能据此认定人员属于同一部门。
- 本期部门凭据映射配置 LinkFox、自研。阿里绘蛙已通知业务不再使用，现有个人配置表中已无相关数据，新的部门 appKey 映射表不配置阿里绘蛙。
- 部门凭据由研发直接通过 SQL 初始化和维护，业务管理员无查看和维护入口。

#### 参考表结构

两张部门表共用下述结构并使用 InnoDB；`departmentId` 与 `rb_department.ID` 对齐，部门采用逻辑关联，不建数据库外键。参考 DDL 要求 MySQL 8.0.16+，研发建表前核对实际库版本及字段类型，建表后确认非空、唯一及 CHECK 约束生效。

| 字段 | 参考类型及默认值 | 用途与规则 |
|---|---|---|
| id | BIGINT，自增主键 | 仅作为数据库内部主键，当前业务表内唯一；两表的 ID 允许相同，不作为任务级凭据引用。 |
| appKeyMappingId | VARCHAR(100)，非空、唯一 | 稳定业务编码，标识本条部门、模型及凭据版本；在本业务表全部记录中唯一，包含停用历史。编码不含真实 appKey，创建后固定、停用后不复用；任务保存此字段。 |
| departmentId | INT，非空 | 本条映射所属的实际部门 ID；不存虚拟“全公司”节点。 |
| providerCode | INT，非空 | 沿用现有模型供应商代码及枚举，不另建编码。 |
| appKey | VARCHAR(1024)，非空 | 保存完整凭据；自研生图为 `Basic <base64(username:password)>`，包含 `Basic` 前缀及空格，沿用现有调用方式。写入前校验非空且完整字符串不超过 1024 个字符，不截断；允许多个部门使用相同值。 |
| isEnabled | TINYINT(1)，非空，默认 1 | 仅允许 0、1，由 CHECK 约束兜底；1 表示参与新任务匹配，0 表示停用并保留历史查询能力。 |
| createdBy、updatedBy | VARCHAR(64)，非空、无默认值 | 填写实际创建及最后维护人的用户ID字符串，不为空或空白；新增时一致，实际变更时更新 updatedBy。 |
| createdTime、updatedTime | DATETIME，非空，默认当前时间 | 创建及最后维护时间；创建时间不变，实际变更时更新最后维护时间。 |
| enabledKey | TINYINT，自动生成 | isEnabled 为 1 时取 1，否则为 NULL，仅用于启用记录唯一约束，不作为业务输入。 |

```sql
-- 美工版部门凭据表的参考 DDL；要求 MySQL 8.0.16+，上线前核对约束实际生效
CREATE TABLE `ai_image_gen_department_model_config` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '部门模型凭据记录ID',
  `appKeyMappingId` VARCHAR(100) NOT NULL COMMENT '任务级凭据映射编码，创建后不变',
  `departmentId` INT NOT NULL COMMENT '映射所属部门ID',
  `providerCode` INT NOT NULL COMMENT '模型供应商代码',
  `appKey` VARCHAR(1024) NOT NULL COMMENT '该记录对应的完整固定凭据',
  `isEnabled` TINYINT(1) NOT NULL DEFAULT 1 COMMENT '是否参与新任务匹配：0=否，1=是',
  `createdBy` VARCHAR(64) NOT NULL COMMENT '创建人用户ID字符串，须显式填写',
  `updatedBy` VARCHAR(64) NOT NULL COMMENT '最后维护人用户ID字符串，须显式填写',
  `createdTime` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updatedTime` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP COMMENT '最后维护时间',
  `enabledKey` TINYINT GENERATED ALWAYS AS (
    CASE WHEN `isEnabled` = 1 THEN 1 ELSE NULL END
  ) VIRTUAL COMMENT '启用记录唯一约束辅助列',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_app_key_mapping_id` (`appKeyMappingId`),
  UNIQUE KEY `uk_department_model_enabled` (`departmentId`, `providerCode`, `enabledKey`),
  CHECK (`isEnabled` IN (0, 1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='AI生图美工版部门模型凭据映射表';

-- 运营版复用字段和索引结构，配置数据独立维护
CREATE TABLE `ai_image_operation_department_model_config`
  LIKE `ai_image_gen_department_model_config`;
ALTER TABLE `ai_image_operation_department_model_config`
  COMMENT='AI生图运营版部门模型凭据映射表';
```

#### 初始化与维护

产品提供“业务、部门 ID、部门名称、LinkFox appKey、自研 appKey”配置清单，各条记录的 appKeyMappingId 在整理初始化数据时一并确认；研发按确认后的清单，按业务、部门及模型分别执行 SQL 插入新表，并填写维护信息。执行前核对实际部门、现有模型枚举及各字段要求；不符合时先修正，不截断或改写原值。真实 appKey 清单另行交付。

- 编码、部门、模型、appKey 及创建信息固定；已有记录只调整启停及最后维护信息，内容未变不更新。初始化填写本次实际操作者的用户ID，后续维护保留创建信息。
- 换凭据时，仅在当前业务表内，对同部门、同模型以同一事务停用旧记录、普通 INSERT 新记录及新编码；失败整笔 ROLLBACK，不覆盖旧记录或部分提交。
- 原映射部门废弃、改由新部门 ID 承接时，业务反馈并确认新部门及对应模型后，由研发在当前业务表内以同一事务停用旧映射、插入新部门对应的新映射及新编码；结费账号未变时沿用原 appKey；维护失败整笔 ROLLBACK。旧映射保留，历史凭据归属不被改写。已外发或无法确认是否外发的任务保留原引用；确认未发送的任务按第 2 节处理。
- 历史记录保留，本期只做新增与启停。停用影响后续凭据匹配；任务使用原凭据及恢复规则见第 2 节，词库查询见第 5 节。

新任务如何选择业务表、校验个人资格、逐级匹配部门凭据并固定任务引用，统一按第 2 节“新任务获取 appKey 完整流程”执行。

### 2. 增加任务级凭据引用

#### 任务字段

本系统美工、运营任务按以下语义保存字段；一个内部任务产生多个外部任务时，各外部任务分别保存对应值。对话生图的接入分工见第 6 节。

| 字段 | 参考类型及默认值 | 用途与规则 |
|---|---|---|
| appKeyMappingId | VARCHAR(100)，默认 NULL | 实际使用的凭据映射编码；按固定业务来源关联对应部门表的同名字段，后续查询原凭据使用此引用。 |
| departmentIdSnapshot | INT，默认 NULL | 首次真正对外提交时，用户实际所属部门 ID；与 rb_department.ID 类型一致，保存本次匹配凭据所用的用户部门，不保存继承命中的上级部门。 |

两字段兼容尚未对外提交及旧规则历史任务的 NULL；新规则首次对外提交前须取得有效值并一起持久化成功，不能用 0、虚拟“全公司”或凭据归属部门代替实际部门。业务来源和模型优先复用现有任务信息；本期不另增凭据归属部门快照字段。

任务业务来源在创建时固定：美工任务引用 `ai_image_gen_department_model_config.appKeyMappingId`，运营任务引用 `ai_image_operation_department_model_config.appKeyMappingId`。优先复用已有业务标识或明确的任务表归属；现有存储无法区分时，在任务凭据引用处补充必要的业务标识。后续不得根据编码内容、当前查询入口、人员部门或哪张表存在记录改换业务。

#### 新任务获取 appKey 完整流程

以下流程在每个新规则外部任务首次真正对外提交前执行，内部排队不视为已对外提交。重新生成及中断恢复按后面的“已提交任务、重试与重新生成”处理。

| 步骤 | 处理逻辑 |
|---|---|
| 1. 确定业务、模型及提交执行者 | 按固定业务和模型选择第 1 节对应的个人配置表、部门凭据表，本部门及上级查找均不跨业务表。复用现有任务领取或执行状态控制，同一外部任务仅取得提交执行权的执行者可以绑定和发送，不得由多个执行者同时处理。 |
| 2. 检查个人资格和额度 | 按第 3 节检查当前业务、用户、模型是否存在未删除且启用的个人配置，并按既有规则检查额度；不满足时不对外提交，结束任务并记录原因。部门有 appKey 不代表用户自动获得生图权限，额度检查、扣减及其他用量处理沿用既有口径。 |
| 3. 读取用户实际部门 | 服务端通过 `userId = rb_admin.ID` 读取 `rb_admin.DepartmentID`，并关联 `rb_department.ID` 确认有效部门；未取得有效部门时失败。本次读取结果同时用于后续凭据匹配和 departmentIdSnapshot，不接受客户端指定快照。 |
| 4. 逐级查找部门映射 | 从步骤 3 的实际部门开始，在当前业务表内按 `departmentId + providerCode` 查找；各级处理见下表，需要向上继承时沿 `rb_department.ParentID` 查找。 |
| 5. 核对命中的映射 | 核对当前业务表中命中映射的 providerCode 与任务固定的模型供应商一致，沿用现有枚举，不从编码名称推断。继承上级时使用实际命中的上级映射编码；多个部门共用 appKey 时仍保存各自实际命中记录的编码，不根据凭据值另选记录。 |
| 6. 保存任务引用 | 保留固定业务来源、模型，将命中记录的 appKeyMappingId 与步骤 3 的实际部门 departmentIdSnapshot 一起持久化；缺少有效值或保存失败时不发送外部请求。 |
| 7. 使用对应 appKey 提交 | 实际请求只使用已成功保存编码对应的真实 appKey，不重新匹配另一份凭据，也不以编码代替第三方凭据；服务商判定该凭据不可用时按本节异常规则处理。 |

步骤 4 在每一级部门按以下规则处理：

| 当前查找部门的配置状态 | 处理规则 |
|---|---|
| 未配置该模型，或该模型仅有停用记录 | 继续查找上一级部门；到达组织顶层仍未找到可用配置时失败。 |
| 该模型存在唯一启用配置，且凭据信息完整 | 命中该配置，停止向上查找；本部门优先于上级部门。 |
| 该模型存在多个启用配置，或启用配置缺少必要凭据信息 | 判为配置异常，不任取一条，也不跳过异常改用上级配置。 |

例如，美工业务中产品组未单独配置 LinkFox，向上命中 IT 部的 LinkFox 映射：任务的 departmentIdSnapshot 保存产品组 ID，appKeyMappingId 保存该映射编码，实际调用使用这条 IT 部映射中的 appKey。测试组若也继承这条映射，可以保存同一编码，但其 departmentIdSnapshot 保存测试组 ID。

凭据归属部门通过“固定业务来源＋appKeyMappingId”取得原映射记录中不变的 departmentId，上例均为 IT 部；实际发起部门取各自的 departmentIdSnapshot，不能用映射部门、用户当前部门或共用 appKey 推断或替代。这里的“凭据归属部门”指命中映射所属部门，实际服务商结费账号由该映射使用的 appKey 决定。

下级独立配置示例：D 部已配置某模型的 appKey，所属 d1 组未单独配置时继承 D 部。若确认 d1 组需使用另一套凭据，则在当前业务表中为 d1 组的部门 ID、该模型配置自己的映射，appKey 可与另一非上级部门 C 部相同。新任务先命中 d1 组映射并停止向上查找，保存 d1 组的映射编码及实际部门快照；不去 C 部查找或引用 C 部的映射，也不改变人员组织归属。具体例外随初始化清单确认，不按人员原部门自动沿用旧凭据。

排队期间调岗，以步骤 3 实际读取的部门为准：页面点击时在 A 部，排队期间 rb_admin.DepartmentID 已更新为 B 部，则首次外发按 B 部匹配并保存 B 部快照；未更新则仍按表中原部门处理。快照仅追溯本次发起归属，不用于重新匹配已提交任务的凭据。

#### 已提交任务、重试与重新生成

已发出外部请求或无法确认是否发出时，不得覆盖原 appKeyMappingId 和 departmentIdSnapshot；已提交任务继续按原关联查询，不因后续个人配置停用或删除而中断。

提交状态依据现有任务状态及提交记录判断：引用已保存不等于已发送，缺少外部任务标识不等于未发送；不能仅凭两个字段是否为空决定发送、重发或转入历史路径。具体恢复方式见下表。

后续查询按“固定业务来源＋appKeyMappingId”读取原 appKey，不要求原记录仍为启用状态，并按步骤 5 核对模型供应商。查询不重新执行当前部门匹配，也不以用户当前部门有效、原映射部门在当前组织中仍启用或可查询为条件；部门废弃不改写任务原快照或映射归属。新规则任务缺少编码、对应业务表内记录缺失或模型供应商不一致时明确报错，不使用错误凭据，也不改用数据库主键 id、当前部门凭据、另一业务表或历史任务路径。

| 场景 | 处理规则 |
|---|---|
| 已取得外部任务标识，查询结果、轮询或查询超时后重试 | 使用原外部任务标识，按原 appKeyMappingId 取得凭据继续查询，departmentIdSnapshot 不变；不因查询重试新建生成任务。 |
| 引用已保存后进程中断，能确认尚未发送请求 | 重新执行上述完整流程，检查资格、额度和当前部门，保存本次匹配的两个字段后使用对应凭据发送。 |
| 首次提交超时或中断，不能确认请求是否发出或服务商是否已创建任务 | 保留本次提交前保存的两个字段，沿用研发核实后的现有服务商查询、重试或人工处理方式，不因切换部门凭据而重新提交。 |
| 人员调岗、部门配置调整或旧配置停用 | 已提交任务的两个字段及结果查询凭据不变；后续新任务重新匹配并保存当前命中编码，词库查询按第 5 节匹配，同次复用、重开刷新及重试仍遵循该节规则。 |
| 用户重新生成，实际创建新的外部任务 | 对新外部任务重新执行上述完整流程，检查资格、额度和当前部门，匹配 appKeyMappingId 并采集 departmentIdSnapshot。 |
| 一个内部任务产生多个外部任务 | 每个外部任务均遵循上述查询、匹配和快照规则。 |
| 服务商已彻底撤销原凭据 | 明确反馈异常并支持人工处理，不能承诺仍可取回结果。 |

是否可安全重发生成请求，取决于现有服务商接口和调用实现对重复请求的处理，不能仅凭“使用同一凭据”认定不会重复生成或计费。研发在实现评审中核实现有任务领取、提交状态及记录能否支撑上述恢复判断，并核实首次提交结果未知时的现有处理方式，按该方式验证本次凭据切换后的行为。

#### 部门与凭据异常

实际生图时确认出现以下异常，直接将任务判为失败，记录具体原因并结束处理，不得通过更换上级、兄弟部门或旧个人凭据继续调用。首次提交超时或中断且结果未知按上表处理，不直接归类为凭据不可用。

| 异常 | 错误原因示例 |
|---|---|
| 未获取到有效所属部门 | 未获取到用户所属部门 |
| 本部门及上级部门均无对应模型的有效凭据 | 所属部门及上级部门未配置 LinkFox 生图凭据（其他模型使用对应名称） |
| 部门配置冲突或启用配置缺少必要凭据信息 | 部门生图配置异常 |
| 映射记录的 providerCode 与任务固定的模型供应商不一致 | 任务凭据与模型不匹配 |
| 已命中的凭据被服务商判定不可用 | 生图凭据不可用 |

失败任务进入「已完成」，结果明确标记为失败，并可查看错误原因，不继续停留在处理中。「已完成」表示任务处理结束，不代表生成成功；错误信息仅描述原因，不包含实际凭据。

### 3. 调整现有个人配置表

美工、运营个人配置继续承载用户授权、quota 和启停。两张表均保留 `appKey`、`appSecret` 字段：`appKey` 按第 6 节完成全部依赖切换后统一置为 `NULL`，此后业务不再读写该字段；`appSecret` 已确认全部为空且未使用，本次保留字段及现有空值，保持不变。

- 每个业务内，同一用户、同一模型最多一条未删除配置，启用和停用均计入；允许保留多条删除历史，由数据库保证并发时也不重复。
- 个人配置未删除、已启用且额度满足要求，才可生图；部门有凭据不自动授予个人权限，新人仍由管理员新增配置。
- 调岗不改变个人 quota 和启停，同部门人员可分别维护额度；剩余额度、用量、扣减及重置沿用既有口径。

quota 字段沿用：total 总额度、scene 场景图、closeUpWhite 白特图、closeUp 特写图、sellPoint 卖点图、aplus 标普A+图额度。

个人配置及部门批量更新均支持结构化填写和 JSON 直填，共用以下规则：

| 项目 | 规则 |
|---|---|
| 对象 | 非空 JSON 对象，至少包含一个字段。 |
| key | 以字母或下划线开头，仅含字母、数字、下划线，不允许重复。 |
| value | 非负整数，允许 0；不接受负数、小数、字符串等值，不新增业务额度上限。 |
| 数据保留 | 输入方式切换、保存和回显不能丢失字段或静默改变数字。 |
| 展示顺序 | 固定为 `total → scene → closeUpWhite → closeUp → sellPoint → aplus`，其他字段随后展示。 |

#### 查询与维护规则

| 项目 | 后端规则 |
|---|---|
| 业务与权限范围 | 美工、运营数据独立；仅指定管理员可访问和操作，授权后可管理当前业务全部人员配置，不按人员或部门限制。 |
| 组织候选 | 两处树均使用全公司当前组织数据；“全公司”为虚拟根，不作为实际部门。异常部门沿用现有口径，搜索不截断节点的完整联动范围。 |
| 人员查询 | 按选中的人员ID查询已有配置，未选表示不限；用户ID精确查询与人员、模型、启停条件共同生效。未配置人员返回空结果，不自动新增；重置清空条件。 |
| 返回与分页 | 列表保留 ID、用户ID、用户名、模型、quota、启停及更新时间，详情增加创建时间；按更新时间倒序，同时间按 ID 倒序，默认 20 条，支持 20/50/100 条。 |
| 新增与编辑 | 新增填写用户ID、用户名、模型及 quota，默认启用；工号仅辅助查询回填。编辑时用户ID、用户名、模型不可变，只修改 quota 和启停。 |
| 保存条件 | 部门缺失或未配置凭据不阻断个人配置保存，不增加部门凭据预检或告警；实际生图异常按第 2 节处理。 |

已完成生图页面的图片可见权限沿用原规则；后续若限制配置管理的数据范围，优先复用其权限能力，查看与修改使用同一范围。

#### 逻辑删除与基础留痕

美工表 `ai_image_gen_model_config` 与运营表 `ai_image_operation_model_config` 分别执行以下规则，删除状态与启停状态独立。

| 信息 | 字段与规则 |
|---|---|
| 创建人、创建时间 | 新增 `createdBy VARCHAR(64) NULL`，复用 `createdTime`；记录创建操作者及时间，后续不覆盖。 |
| 更新人、更新时间 | 新增 `updatedBy VARCHAR(64) NULL`，复用 `updatedTime`；新增时与创建信息一致，实际变更时记录最后操作者及时间。 |
| 删除时间 | 新增 `deletedTime DATETIME NULL`；为空表示未删除，非空表示已删除。 |
| 启停 | 沿用 `isEnabled`，非空、默认 1，仅允许 0、1；服务端和数据库均校验，删除及恢复不改变原启停值。 |

管理员操作者由服务端取当前登录用户ID，不接受客户端指定；脚本初始化的新配置，创建人和更新人均记为 `system`。新增须填写创建、更新信息，编辑、启停、删除、恢复及批量更新发生实际变更时填写最后更新信息；无变化或重复操作不刷新留痕。必填操作者缺失、为空、纯空白或超过 64 个字符时拒绝写入，不截断。

存量配置初始化为未删除，保留已有时间；未知历史操作者留空，不补造、不影响后续正常维护。存量启停值异常须核实处理后再上线约束，不能静默改值。本期仅保留创建及最后维护信息，不增加逐次操作日志，操作者字段不新增前端展示。

| 操作 | 规则 |
|---|---|
| 删除 | 保留原记录及业务数据，只写删除时间和最后更新信息。已删除配置不参与日常查询、维护、批量更新及新任务资格判断，日常接口也不能通过旧ID继续操作。 |
| 删除后重新新增 | 生成新配置ID及创建信息，使用本次填写的 quota、启停值，保留旧记录；同一用户、模型已有未删除配置时提示已存在，不覆盖。 |
| 历史任务与用量 | 已提交任务按原关联继续查询，既有用量确认、扣减和返还沿原时点及口径处理；不能因配置删除、重新新增或恢复而中断、漏记、重复处理、错误关联或重置已耗额度。 |
| 后台恢复 | 仅授权研发核对后操作，且同业务、用户、模型没有其他未删除配置。只清空删除时间并更新最后维护信息，原 ID、用户、模型、quota、启停及创建信息不变；恢复后按当前规则判断新任务资格。业务页面不增加恢复入口。 |
| 并发与重复操作 | 新增或恢复并发时最多一条未删除配置，冲突操作失败且原记录保持不变；重复删除、恢复不改写留痕。编辑与删除并发时按实际落库结果反馈。 |

本系统、对话生图及其他读写方完成适配，并验证历史任务查询和用量处理后，才启用逻辑删除；上线与回退统一按第 6 节执行。回退须保留新增字段及上述规则，兼容删除历史与新配置共存，不通过删除历史或覆盖新配置恢复旧约束。

### 4. 改造按部门批量额度更新

将原按 appKey 更新的范围改为当前业务页面的“部门＋模型”，提交后整份覆盖命中配置的 quota。

| 项目 | 业务规则 |
|---|---|
| 权限与输入 | 按第 3 节权限范围执行，部门集合、生图模型及完整 quota 均必填；服务端校验权限、部门、模型及 quota，不仅依赖前端校验。 |
| 部门范围 | 仅按最终勾选的实际部门去重执行，半选父节点本身不计入，不重新纳入已取消的下级。“全公司”展开为实际部门，不作为部门ID提交。 |
| 人员与配置范围 | 服务端按组织归属确定人员，匹配当前业务、所选模型的已有未删除配置，包含停用配置；不受列表筛选或分页限制，不自动新增配置。 |
| 更新内容 | 整份覆盖 quota，未填写的原字段被移除；仅实际变化的配置更新额度及最后维护信息，其他业务数据不变。内容相同的配置保留原更新人及更新时间。 |
| 无有效部门 | 不参与部门批量更新，选择全公司时也不例外；保留原配置，仍可单独维护。 |

#### 范围与执行规则

- 人员范围按本次成功取得的完整组织数据一次确定；此前生效的调岗影响本批，此后变化影响下一次操作，不边更新边重算。
- 在该人员范围内确定本批配置。确定前已删除并重新新增的有效配置可命中；确定后不补入新增或重建配置，每条只处理一次。
- 本批额度及维护信息必须全部生效或全部不生效。与个人编辑、启停、删除同时发生时，按明确的先后顺序处理，不覆盖其他业务字段；无法完整完成时整批失败，不能跳过冲突记录后提示成功。

#### 执行结果与再次提交

| 执行结果 | 处理规则 |
|---|---|
| 校验或组织读取失败 | 未授权、任一参数无效（含不存在或虚拟部门），或组织数据读取失败、不完整时，整批不更新；提示具体原因并保留输入，不能当作无命中。 |
| 成功 | 确认本批全部处理成功后提示成功，关闭抽屉并刷新列表；有命中但内容全部相同，也按成功处理。 |
| 无命中 | 参数合法且组织数据完整，但没有符合条件的配置；提示“未命中任何记录”并保留输入。 |
| 确认执行失败 | 确认本批已停止且全部未生效后，提示失败并保留输入；不能留下部分更新，也不影响其他操作已生效的变更。 |
| 结果未确认 | 响应超时、连接中断或未收到明确结果时，提示“更新结果暂未确认，请刷新列表核对后再操作”并保留输入；不直接认定成功或失败，不自动重发。 |

沿用现有抽屉流程，校验通过后直接提交，处理中避免重复操作。结果未确认时，用户先刷新核对；手动再次提交视为新请求，重新按当时组织归属及有效配置确定范围。

### 5. LinkFox 词库查询改用部门凭据

本次将美工、运营新增、编辑、查看、批量导入及批量修改入口的词库候选列表和名称回显，统一改用用户当前部门的 LinkFox 凭据。交互、仅保存 `sensitiveLibraryId`、`replaceLibraryId`、分页、同次复用、重开刷新及重试规则，沿用 [M-38039 敏感词库与替换词库](https://github.com/xuqiang97/ai-image-banned-word)。

- 沿用查询 userId 来源、业务和权限，按第 1、2 节为用户当前部门匹配 LinkFox 凭据，不使用个人 appKey 或任务历史凭据查询词库。
- 服务端继续调用 `POST /linkfox-ai/image/v2/material/list`，敏感词库 `type="11"`、替换词库 `type="12"`。同次查询的两类词库及各分页使用同一凭据，不混用结果，不向业务前端返回真实 appKey。
- 查询及重试不新增生图额度校验、不扣额度、不触发生图，也不改写任务凭据引用、部门快照或任务状态。历史任务的引用及快照为空不阻断词库查询，也不补填；生图结果查询仍按第 2、6 节使用原凭据关联。

| 状态 | 处理规则 |
|---|---|
| 正在查询或正常自动分页 | 有原 ID 时显示“正在加载词库名称”及完整 ID，不判为失败。 |
| 完整列表不含原 ID | 显示“词库当前不可选”及完整 ID，不据此断言已删除；不自动清空、同名替换或用旧凭据补查。可编辑入口仅在用户明确更换或清空并保存后修改对应 ID，查看保持只读。 |
| 无有效部门或映射、配置或凭据异常、接口失败或分页异常未取齐 | 有原 ID 时保留并显示“词库加载失败”，不能显示为空列表或“词库当前不可选”；无法取得有效凭据时不调用词库接口。 |
| 查看时未选词库 | 显示“未选择”。 |

用户未明确更改时，保存、提交及复制重跑保留原 ID；不新增词库可用性预检或拦截。实际生图按第 2 节匹配提交时的凭据并原样传递 ID；上游明确拒绝时沿用既有失败处理，不清空 ID 或删除词库参数重试。

#### 历史任务兼容

以本系统实际切换到部门凭据的时点为界，结合首次外发记录和任务状态区分新旧规则；不能仅凭创建时间或字段空值判定。建表、后续换部门或换凭据不重置边界，依据不足时反馈异常并核对，不自动走历史路径。

- 切换前已外发：通过稳定保留的原凭据关联继续查询和处理用量，不能按 userId 改取当前个人配置。个人配置变更或 appKey 置空前，须保留所需原值及关联；部门废弃、个人配置删除或重建不影响原任务。无需全量回填任务字段，未知历史部门的 departmentIdSnapshot 保持 NULL，不补造、不因此阻断查询。
- 切换后首次外发，含切换前创建的排队任务：完整执行第 2 节，必要字段或记录异常时报错，不转入历史路径。
- 历史任务未结束或仍有相关依赖时，持续保留原凭据及关联。凭据或关联缺失、原凭据被服务商撤销时，明确反馈异常并人工核对，不改用当前凭据或承诺恢复。

#### 回退要求

实际切换前，在验证环境用切换后的任务和配置数据验证拟回退版本；未通过则不切换。

| 验证对象 | 回退后的要求 |
|---|---|
| 旧规则已外发任务 | 按上述历史兼容规则继续查询和处理用量。 |
| 新规则已外发任务 | 按第 2 节使用原引用及外部任务标识查询和处理用量，业务来源、凭据引用及部门快照不变。 |
| 回退后首次外发任务，含排队任务 | 完整执行第 2 节，按提交时的实际部门匹配凭据。 |
| 词库查询及名称回显 | 按第 5 节使用当前部门凭据，原 ID 及异常处理规则不变，不重新依赖个人 appKey。 |

验证包含新增、删除重建及新旧配置共存；回退保留第 3 节字段和规则、任务原归属及引用，不重置切换边界。个人 appKey 置空前，再以 NULL 状态复验以上场景。

切换后，业务页面及其接口数据、导出、普通日志和错误提示均不含真实 appKey，业务端旧写入入口关闭。appKeyMappingId 仅为内部标识，可按现有权限用于任务信息和排查，不作鉴权，也不因此新增页面或列表字段。

## 验收标准

以下 A01–A54 按八类场景覆盖本系统美工、运营及对话生图接入确认。页面交互见 HTML 原型，词库交互见第 5 节关联需求，数据规则以对应后端章节为准；后端能力及实际生图结果须由研发实现后验证，静态原型不能代替验收。
