## 需求概述

一期在个人模型配置中维护 appKey，人员调岗后需要逐人调整，容易产生费用归属错误；多个小组共用凭据时，按 appKey 批量修改也无法准确区分小组。

本期覆盖美工、运营管理员配置及相关生图任务：**将 appKey 从个人配置中拆出，按部门统一管理；新任务按当前部门获取凭据，提交后固定使用该次凭据。个人配置继续负责生图授权和额度。**

| 本期改动 | 具体做什么 | 解决的业务问题 |
|---|---|---|
| 1. 新增部门级 appKey 映射表 | 美工、运营分别建表、复用结构，各自在业务内建立“部门＋模型 → appKey”关系；本部门优先，支持上级继承及多个部门共用凭据，由授权研发维护。 | 减少逐人维护 appKey；调岗后新任务自动按当前业务和部门匹配，避免费用归属错误。 |
| 2. 增加任务级凭据引用 | 首次对外提交前保存 appKeyMappingId 和实际发起部门快照 departmentIdSnapshot；凭据归属部门通过映射记录获取，后续查询沿用原凭据。 | 避免调岗、换 key 后旧任务查不到结果，保留费用归属依据。 |
| 3. 调整现有个人配置表 | 保留用户、模型、quota、启停；迁出 appKey，清理未使用的 appSecret，增加创建人、更新人及逻辑删除。 | 明确个人配置职责，保留个性化额度，支持误操作排查。 |
| 4. 改造批量额度更新逻辑 | 从按 appKey 更新改为按“部门＋模型”更新已有人员配置，整份覆盖 quota，保留启停状态。 | 共用 appKey 的多个小组可以分别调整额度。 |
| 5. 完成本系统与对话生图的切换 | 先完成对话生图的新凭据读取，再切换本系统配置流程；保留历史任务查询能力，依赖退出后再清理个人 appKey。 | 避免切换期间新增配置、其他项目或历史任务受影响。 |

以上五项均纳入本期交付，后端规则按相同顺序展开。部门映射表参考结构见第 1 节，任务按第 2 节保存固定业务来源、appKeyMappingId 及 departmentIdSnapshot；具体任务表适配及接口实现由研发结合现有实现确定。

## 前端改动与原型

美工、运营保持两个独立管理页面，移除 appKey 相关入口，配置用户改为组织树查询，批量更新改为按部门及必选模型执行。工号查询、个人配置及 quota 编辑沿用现有功能，具体页面、字段文案和交互见 [HTML 原型](index.html)，数据规则和验收以本文为准。

人员选择复用[运营已完成生图页](https://web.zhcxkj.com/SMS/#/PMS/PMS_SUB/AiImageOperation/AICompletedRawImage)的创建人控件交互，部门选择复用[用户列表页](https://web.zhcxkj.com/SMS/#/SMS/SMS_SUB/AuthorityManage/UserList)；本期管理范围按第 3 节执行。

原型使用虚构数据，不连接真实接口，刷新后恢复；顶部【本期前端改动】仅供评审。后端能力须实现后验收。顶部线上链接对应已发布版本，本地修改发布后才会同步。

## 后端改动

### 1. 新增部门级 appKey 映射表

美工、运营分别新增部门级映射表，与现有个人配置表保持相同的业务划分。两张部门表复用字段、索引及维护规则，数据独立，不自动同步凭据或启停状态。

| 业务 | 现有个人配置表 | 新增部门凭据表 |
|---|---|---|
| 美工版 | `ai_image_gen_model_config` | `ai_image_gen_department_model_config` |
| 运营版 | `ai_image_operation_model_config` | `ai_image_operation_department_model_config` |

新任务先按所属业务确定对应的个人配置表和部门凭据表，再检查授权、额度并匹配部门凭据。对话生图沿用原个人配置读取链路的业务归属选取对应部门表，具体切换见第 5 节；不能因某张表存在记录而改用另一业务。

部门归属统一通过用户配置的 `userId = rb_admin.ID` 取得 `rb_admin.DepartmentID`，再关联 `rb_department.ID`；上级关系使用 `rb_department.ParentID`。用户ID不是工号，`rb_department.LeaderID` 表示负责人，兼管部门不改变员工个人归属。

按部门选人、批量额度更新和新任务凭据匹配均使用上述组织数据，个人配置不另存部门归属。部门改名不改变其匹配身份；新增部门、层级及人员归属变化后，下次读取按最新记录处理，时效沿用现有组织系统。

- 每张业务表内按生图模型分别配置，同模型、同部门同时只能有一个有效配置；两个业务可分别为同一部门、同一模型配置凭据，特殊部门可独立配置。
- 多个部门允许共用同一凭据，不能据此认定人员属于同一部门。
- 本期涉及 LinkFox、自研以及已停用的阿里绘蛙历史配置；后者仅保留历史配置和任务处理能力，不恢复新任务。
- 部门凭据由授权研发低频、受控维护并保留变更记录，业务管理员无查看和维护入口。
- 凭据变更不得覆盖或删除仍被任务使用的历史凭据；已有任务按第 2 节继续使用原凭据。

**参考表结构**

以下字段结构两张部门表通用，沿用已提供的个人配置表的 InnoDB 和字段风格；参考 DDL 要求 MySQL 8.0.16 及以上版本，以执行 CHECK 约束。`departmentId` 与 `rb_department.ID` 对齐为 INT，`providerCode` 和 `appKey` 分别沿用现有 INT、VARCHAR(100)。部门采用逻辑关联，由现有组织数据核对，不要求与组织表建立数据库外键。研发上线前核对实际库版本及字段定义，并验证下述取值、非空及唯一约束实际生效。

| 字段 | 参考类型及默认值 | 用途与规则 |
|---|---|---|
| id | BIGINT，自增主键 | 仅作为数据库内部主键，当前业务表内唯一；两表的 ID 允许相同，不作为任务级凭据引用。 |
| appKeyMappingId | VARCHAR(100)，非空、唯一 | 可命名的稳定业务编码，标识本条部门、模型及凭据版本；在本业务表全部记录中唯一，包含停用历史。任务保存此字段。 |
| departmentId | INT，非空 | 本条映射所属的实际部门 ID；不存虚拟“全公司”节点。 |
| providerCode | INT，非空 | 沿用现有模型供应商代码及枚举，不另建编码。 |
| appKey | VARCHAR(100)，非空 | 本条记录对应的凭据；写入前校验非空且长度符合字段定义，不截断凭据；允许多个部门使用相同值。 |
| isEnabled | TINYINT(1)，非空，默认 1 | 仅允许 0、1，由 CHECK 约束兜底；1 表示参与新任务匹配，0 表示停用并保留历史查询能力。 |
| createdBy、updatedBy | VARCHAR(64)，非空、无默认值 | 必须显式填写创建及最后维护人的用户ID字符串，脚本拒绝空字符串或纯空白；新增时一致，实际改变启停状态时更新 updatedBy。 |
| createdTime、updatedTime | DATETIME，非空，默认当前时间 | 创建及最后维护时间；创建时间不变，实际变更时更新最后维护时间。 |
| enabledKey | TINYINT，自动生成 | isEnabled 为 1 时取 1，否则为 NULL，仅用于启用记录唯一约束，不作为业务输入。 |

```sql
-- 美工版部门凭据表的参考 DDL；要求 MySQL 8.0.16+，上线前核对约束实际生效
CREATE TABLE `ai_image_gen_department_model_config` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '部门模型凭据记录ID',
  `appKeyMappingId` VARCHAR(100) NOT NULL COMMENT '任务级凭据映射编码，创建后不变',
  `departmentId` INT NOT NULL COMMENT '映射所属部门ID',
  `providerCode` INT NOT NULL COMMENT '模型供应商代码',
  `appKey` VARCHAR(100) NOT NULL COMMENT '该记录对应的固定凭据',
  `isEnabled` TINYINT(1) NOT NULL DEFAULT 1 COMMENT '是否参与新任务匹配：0=否，1=是',
  `createdBy` VARCHAR(64) NOT NULL COMMENT '创建人用户ID字符串，须显式填写',
  `updatedBy` VARCHAR(64) NOT NULL COMMENT '最后维护人用户ID字符串，须显式填写',
  `createdTime` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updatedTime` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP COMMENT '最后维护时间',
  `enabledKey` TINYINT GENERATED ALWAYS AS (
    CASE WHEN `isEnabled` = 1 THEN 1 ELSE NULL END
  ) VIRTUAL COMMENT '启用记录唯一约束辅助列',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_app_key_mapping_id` (`appKeyMappingId`),
  UNIQUE KEY `uk_department_model_enabled` (`departmentId`, `providerCode`, `enabledKey`),
  CHECK (`isEnabled` IN (0, 1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='AI生图美工版部门模型凭据映射表';

-- 运营版复用字段和索引结构，配置数据独立维护
CREATE TABLE `ai_image_operation_department_model_config`
  LIKE `ai_image_gen_department_model_config`;
ALTER TABLE `ai_image_operation_department_model_config`
  COMMENT='AI生图运营版部门模型凭据映射表';
```

上述 [CREATE TABLE ... LIKE](https://dev.mysql.com/doc/refman/8.0/en/create-table-like.html) 复用字段、生成列、索引及 CHECK 定义，不复制配置数据；两张表分别初始化和维护。

MySQL 自 [8.0.16 起执行 CHECK 约束](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)。本表通过 CHECK 拒绝 0、1 之外的启停值，通过 NOT NULL 拒绝空值；维护人缺失、空字符串或纯空白仍须由维护程序或脚本在执行写入前拒绝。

两项唯一约束在各业务表内分别生效：appKeyMappingId 对全部记录唯一，停用后也不能复用；同部门、同模型只能有一条启用记录，允许保留多条停用历史。appKey 不设唯一索引，不同部门共用 appKey 时仍分别创建自己的 appKeyMappingId。启用记录约束使用 MySQL 的[生成列索引](https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html)和[唯一索引允许多个 NULL 值](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)的能力。

**映射编码命名**

appKeyMappingId 由授权研发在创建记录时命名，长度不超过 100 个字符，仅使用大写英文字母、数字和下划线；美工以 `GEN_` 开头，运营以 `OP_` 开头，前缀后须有内容。建议组合部门简称、模型及版本，例如 `GEN_IT_LINKFOX_001`、`OP_IT_LINKFOX_001`。这些是内部业务编码，不包含真实 appKey，也不能用于第三方鉴权；命名中的部门、模型说明仅供识别，实际匹配仍使用 departmentId、providerCode。

部门有效性、模型枚举、编码非空、格式、长度及业务前缀、appKey 非空和长度、isEnabled 取值、维护人非空及长度均由维护程序或脚本在写入前校验，校验失败不写入，不静默截断或改写编码、凭据及维护人；DDL 本身不承担全部业务校验。

**凭据维护与历史保留**

- 每条记录的 appKeyMappingId、departmentId、providerCode、appKey 及创建信息保持不变；受控维护程序或脚本只允许更新 isEnabled、updatedBy、updatedTime，拒绝原地修改固定字段，部门改名也不修改已创建的编码。需要调整映射或凭据时使用新记录和新编码。用户、quota、部门名称及层级继续取现有数据，不存入本表；本表不增加 appSecret。
- 更换凭据仅操作当前业务表：同部门、同模型在同一事务内停用当前记录并新增启用记录及新的 appKeyMappingId，例如从 `GEN_IT_LINKFOX_001` 更换为 `GEN_IT_LINKFOX_002`。新增使用普通 INSERT，不以替换或冲突更新覆盖旧记录；两步一起生效，不影响另一业务表。维护程序或脚本捕获任一步错误后必须显式整笔 ROLLBACK，不继续 COMMIT；编码重复或并发唯一约束冲突时反馈失败并核对当前配置，不能留下半完成的切换。InnoDB 的[重复键错误只回滚当前语句](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html)，不能仅凭语句报错认定整笔事务已回滚。
- 本期不提供部门凭据记录的删除操作，日常维护通过新增与启停完成，历史记录保留；不新增独立删除状态，历史数据清理不纳入本期。
- 停用仅改变新任务的匹配结果，后续新任务按既定上级继承规则处理。已发出外部请求或发送结果未知的任务，其 appKeyMappingId 不变；按编码查询原凭据时不加 isEnabled = 1 条件，继续保留任务及过渡、回退流程所需的原凭据关联。能确认尚未发送的任务按第 2 节恢复规则处理。
- 授权研发维护时显式填写实际操作者的用户ID字符串；确实由初始化脚本创建记录时，createdBy、updatedBy 均填写 `system`，人工维护不能用 system 代替实际操作者。两张部门表均为本期新建，即使凭据来自旧个人配置，仍记录本次创建映射的操作者，不沿用“历史未知留空”的规则；个人配置表的存量兼容按第 3 节执行。创建信息不变，内容未变不更新维护人和维护时间。旧凭据记录及基础留痕用于核对变更，本期不另建逐次操作流水。

新任务如何选择业务表、校验个人资格、逐级匹配部门凭据并固定任务引用，统一按第 2 节“新任务获取 appKey 完整流程”执行。

### 2. 增加任务级凭据引用

**任务字段**

美工、运营及对话生图的相关任务按以下语义保存字段；一个内部任务产生多个外部任务时，各外部任务分别保存对应值。

| 字段 | 参考类型及默认值 | 用途与规则 |
|---|---|---|
| appKeyMappingId | VARCHAR(100)，默认 NULL | 实际使用的凭据映射编码；按固定业务来源关联对应部门表的同名字段，后续查询原凭据使用此引用。 |
| departmentIdSnapshot | INT，默认 NULL | 首次真正对外提交时，用户实际所属部门 ID；与 rb_department.ID 类型一致，保存本次匹配凭据所用的用户部门，不保存继承命中的上级部门。 |

两字段可在尚未对外提交或旧规则历史任务中为空；按新规则首次对外提交前必须取得有效值并一起持久化成功，不能用 0、虚拟“全公司”或凭据归属部门代替实际部门。字段可为空用于兼容存量及排队阶段，不放宽新任务的提交要求。业务来源和模型优先复用现有任务信息；本期不另增凭据归属部门快照字段。

任务沿用创建时确定的业务来源：美工任务引用 `ai_image_gen_department_model_config.appKeyMappingId`，运营任务引用 `ai_image_operation_department_model_config.appKeyMappingId`。业务来源优先复用任务已有业务标识或明确的任务表归属；若现有存储无法区分，研发在任务凭据引用处补充必要的业务标识。后续始终按该固定业务选表，不能根据编码前缀、当前查询入口、人员部门或哪张表存在记录改换业务。

**新任务获取 appKey 完整流程**

以下流程在新规则任务首次真正对外提交前执行，内部排队不视为已对外提交；重新生成所创建的新外部任务也按此流程处理。中断恢复时能否重新执行本流程，按后面的“已提交任务、重试与重新生成”判断。

| 步骤 | 处理逻辑 |
|---|---|
| 1. 确定业务、模型及提交执行者 | 按任务固定业务和模型，选择第 1 节对应的个人配置表、部门凭据表；对话生图沿用原个人配置读取链路的业务归属。本部门及上级查找均不跨业务表。同一外部任务复用现有任务领取或执行状态控制，仅取得提交执行权的执行者可以绑定和发送，不能由多个执行者同时处理。 |
| 2. 检查个人资格和额度 | 按第 3 节检查当前业务、用户、模型是否存在未删除且启用的个人配置，并按既有规则检查额度；不满足时不对外提交，结束任务并记录原因。部门有 appKey 不代表用户自动获得生图权限，额度检查、扣减及其他用量处理沿用既有口径。 |
| 3. 读取用户实际部门 | 服务端通过 `userId = rb_admin.ID` 读取 `rb_admin.DepartmentID`，并关联 `rb_department.ID` 确认有效部门；未取得有效部门时失败。本次读取结果同时用于后续凭据匹配和 departmentIdSnapshot，不接受客户端指定快照。 |
| 4. 逐级查找部门映射 | 从步骤 3 取得的实际部门开始，在当前业务表内按 `departmentId + providerCode` 查找；仅未配置或已停用时沿 `rb_department.ParentID` 向上查找。唯一且完整的启用记录即命中，配置异常或到顶仍未命中时失败，具体见下表。 |
| 5. 核对命中的映射 | 检查 appKeyMappingId 的业务前缀与任务一致，且映射 providerCode 与任务固定的模型供应商一致，沿用现有枚举，不从编码名称推断。继承上级时使用实际命中的上级映射编码；多个部门共用 appKey 时仍保存各自实际命中记录的编码，不根据凭据值另选记录。 |
| 6. 保存任务引用 | 保留固定业务来源、模型，将命中记录的 appKeyMappingId 与步骤 3 取得的实际部门 departmentIdSnapshot 一起持久化，快照不保存继承命中的上级部门。缺少有效值或保存失败时不发送外部请求，避免外部任务已创建而本系统缺少引用。 |
| 7. 使用对应 appKey 提交 | 实际请求使用已成功保存的 appKeyMappingId 所对应记录中的真实 appKey，编码本身不能代替第三方凭据；不得保存一个编码后再次按当前部门匹配另一份凭据发送。服务商判定已命中凭据不可用时任务失败，不再换上级、兄弟部门或旧个人凭据尝试。 |

步骤 4 在每一级部门按以下规则处理：

| 当前查找部门的配置状态 | 处理规则 |
|---|---|
| 未配置该模型，或该模型的配置已停用 | 继续查找上一级部门；到达组织顶层仍未找到可用配置时失败。 |
| 该模型存在唯一启用配置，且凭据信息完整 | 命中该配置，停止向上查找；本部门优先于上级部门。 |
| 该模型存在多个启用配置，或启用配置缺少必要凭据信息 | 判为配置异常，不任取一条，也不跳过异常改用上级配置。 |

组织继承仅处理未配置或已停用的情况，不作为调用失败后的换凭据策略；具体异常反馈见本节“部门与凭据异常”。

例如，美工业务中产品组未单独配置 LinkFox，向上命中 IT 部的 `GEN_IT_LINKFOX_001`：任务的 departmentIdSnapshot 保存产品组 ID，appKeyMappingId 保存该编码，实际调用使用这条 IT 部映射中的 appKey。测试组若也继承这条映射，可以保存同一编码，但其 departmentIdSnapshot 保存测试组 ID。

凭据归属部门通过“固定业务来源＋appKeyMappingId”取得原映射记录的 departmentId；该字段创建后不变、历史记录保留，因此任务不重复保存凭据归属部门。上例两组任务的凭据归属部门均为 IT 部，实际发起部门分别来自各自的 departmentIdSnapshot，不能用映射部门或用户当前部门替代，也不能根据共用 appKey 推断归属。

排队期间发生调岗时，以步骤 3 实际读取的部门为准。例如页面点击提交时在 A 部、排队期间 rb_admin.DepartmentID 更新为 B 部，首次对外提交时按 B 部匹配并保存 B 部 ID；该字段尚未更新时仍按表中的原部门处理。departmentIdSnapshot 用于追溯本次任务发起归属，不用于重新匹配已提交任务的凭据。

**已提交任务、重试与重新生成**

任务已发出外部请求或无法确认是否发出时，重复执行不得覆盖原 appKeyMappingId 和 departmentIdSnapshot。已对外提交的任务继续按原关联查询，不因后续个人配置停用或删除而中断。

字段保存成功不代表外部请求已经发出，缺少外部任务标识也不代表请求尚未发送。进程中断后，根据现有任务状态及提交记录恢复：能确认尚未发送时，重新执行上述完整流程，检查资格、额度和当前部门，保存本次引用后发送；无法确认是否发送时，保留原引用，按提交结果未知处理。仅凭两个字段是否为空，不能决定发送、重发或转入历史路径。

后续查询按“固定业务来源＋appKeyMappingId”获取原记录的 appKey，不重新按当前部门匹配，也不要求原记录仍为启用状态。提交及后续查询取凭据时，均须核对映射记录的 providerCode 与任务固定的模型供应商一致，沿用现有枚举，不从编码名称推断模型。部门更换凭据后，新任务保存新编码，已提交任务继续使用旧编码。新规则任务缺少编码、编码前缀与业务不符、对应记录缺失或模型供应商不一致时明确反馈异常，不使用错误凭据，也不改用数据库主键 id、当前凭据、另一业务表或历史任务路径。

| 场景 | 处理规则 |
|---|---|
| 已取得外部任务标识，查询结果、轮询或查询超时后重试 | 使用原外部任务标识，按原 appKeyMappingId 取得凭据继续查询，departmentIdSnapshot 不变；不因查询重试新建生成任务。 |
| 引用已保存后进程中断，现有状态及提交记录能确认尚未发送请求 | 恢复时按首次提交规则重新检查资格、额度和当前部门，保存本次匹配的两个字段，再使用对应凭据发送；不能仅因字段已有值就视为已提交。 |
| 首次提交超时或中断，不能确认请求是否发出或服务商是否已创建任务 | 保留本次提交前已保存的 appKeyMappingId 和 departmentIdSnapshot，不能因缺少外部任务标识认定未创建任务；沿用研发核实后的现有服务商查询、重试或人工处理方式，不因切换部门凭据而重新提交。 |
| 人员调岗、部门配置调整或旧配置停用 | 不改变已提交任务的 appKeyMappingId 和 departmentIdSnapshot；调整只影响后续新任务。 |
| 用户重新生成，实际创建新的外部任务 | 重新检查资格、额度和当前部门，为新外部任务重新匹配 appKeyMappingId 并采集 departmentIdSnapshot。 |
| 一个内部任务产生多个外部任务 | 每个外部任务均遵循上述查询、匹配和快照规则。 |
| 服务商已彻底撤销原凭据 | 明确反馈异常并支持人工处理，不能承诺仍可取回结果。 |

是否可安全重发生成请求，取决于现有服务商接口和调用实现对重复请求的处理，不能仅凭“使用同一凭据”认定不会重复生成或计费。研发在实现评审中核实现有任务领取、提交状态及记录能否支撑上述恢复判断，并核实首次提交结果未知时的现有处理方式，按该方式验证本次凭据切换后的行为。

**部门与凭据异常**

实际生图时确认出现以下异常，直接将任务判为失败，记录具体原因并结束处理，不得通过更换上级、兄弟部门或旧个人凭据继续调用。首次提交超时或中断且结果未知按上表处理，不直接归类为凭据不可用。

| 异常 | 错误原因示例 |
|---|---|
| 未获取到有效所属部门 | 未获取到用户所属部门 |
| 本部门及上级部门均无对应模型的有效凭据 | 所属部门及上级部门未配置 LinkFox 生图凭据（其他模型使用对应名称） |
| 部门配置冲突或启用配置缺少必要凭据信息 | 部门生图配置异常 |
| 映射记录的 providerCode 与任务固定的模型供应商不一致 | 任务凭据与模型不匹配 |
| 已命中的凭据被服务商判定不可用 | 生图凭据不可用 |

失败任务进入「已完成」，结果明确标记为失败，并可查看错误原因，不继续停留在处理中。「已完成」表示任务处理结束，不代表生成成功；错误信息仅描述原因，不包含实际凭据。

### 3. 调整现有个人配置表

美工、运营个人配置继续承载用户授权、quota 和启停；appKey 按第 5 节分阶段退出。两张表的 `appSecret` 已确认全部为空且未使用，本期清理该字段及实体、读写映射，不纳入部门凭据配置。

- 当前业务页面内，同一用户、同一模型最多存在一条未删除配置，启用和停用配置共同受此约束；已删除记录作为历史保留。
- 没有未删除配置、配置停用或额度不足，均按现有规则拒绝生图；部门存在有效凭据不等于人员获得授权，新人仍需管理员手动新增配置。
- 调岗不自动改变用户启停和个性化 quota；同部门不同人可以有不同 quota，并可单独维护。
- 剩余额度、用量、扣减及重置沿用既有口径。

quota 字段沿用：total 总额度、scene 场景图、closeUpWhite 白特图、closeUp 特写图、sellPoint 卖点图、aplus 标普A+图额度。

quota 支持结构化填写和 JSON 直填，两种方式共用以下校验，适用于个人配置及部门批量更新：

| 项目 | 规则 |
|---|---|
| 对象 | 非空 JSON 对象，至少包含一个字段。 |
| key | 以字母或下划线开头，仅含字母、数字、下划线，不允许重复。 |
| value | 非负整数，允许 0；不接受负数、小数、字符串等值，不新增业务额度上限。 |
| 数据保留 | 输入方式切换、保存和回显不能丢失字段或静默改变数字。 |
| 展示顺序 | 固定为 `total → scene → closeUpWhite → closeUp → sellPoint → aplus`，其他字段随后展示。 |

| 人员查询 | 按最终选中的人员ID集合查询已有配置；未选人员表示不限人员条件。用户ID精确查询与人员、模型、启停条件共同生效；未配置人员返回空结果，不自动新增。重置清空查询条件。 |

已完成生图页面的图片可见权限继续沿用原规则。后续如需限制配置管理的数据范围，优先复用其权限能力，查看与修改使用同一范围；具体授权规则及验收由后续业务需求确定。

**逻辑删除与基础留痕**

美工表 `ai_image_gen_model_config` 与运营表 `ai_image_operation_model_config` 采用同一套规则，各自保持独立业务范围。采用“逻辑删除保留旧记录，重新新增创建新记录”的方式；删除状态由 `deletedTime` 判断，与 `isEnabled` 启停状态分开。

| 信息 | 字段与规则 |
|---|---|
| 创建人、创建时间 | 新增 `createdBy VARCHAR(64) NULL`，复用 `createdTime`；服务端以字符串记录当前登录管理员的用户ID，后续操作不覆盖。 |
| 更新人、更新时间 | 新增 `updatedBy VARCHAR(64) NULL`，复用 `updatedTime`；新增时与创建信息一致，实际变更 quota、启停或删除状态时记录本次操作者及时间。批量更新对实际发生变更的每条配置同步记录，内容未变的记录保持原更新信息。 |
| 逻辑删除 | 新增 `deletedTime DATETIME NULL`；为空表示未删除，非空表示已删除。删除时同时写入 `updatedBy`、`updatedTime`，由最后更新人标识删除操作者，并保留原 quota、启停及其他业务信息。 |
| SQL 批量初始化 | 由初始化脚本新建的配置，显式写入 `createdBy = 'system'`、`updatedBy = 'system'` 及相应时间；后续管理员修改时保留创建信息，更新人改为实际操作者的用户ID字符串。 |
| 存量数据 | 现存记录初始化为未删除，保留已有时间；无法确认的历史创建人、更新人留空。`system` 仅表示实际系统初始化或自动处理，不用于补填未知历史。 |

操作者字段记录执行配置操作的人，区别于被配置人员的 `userId`；管理员操作由服务端登录身份取得，不接受客户端指定，`system` 为约定的系统标识。本期仅在配置表保留当前内容、创建信息和最后更新信息，不记录逐次操作历史或修改前后快照；本期不新增操作者字段的前端展示。

**未删除配置唯一约束：** 两张表均以如下约束替换原 `uk_user_model(userId, providerCode)`。`undeletedKey` 是数据库自动计算的辅助列；未删除时为 `1`，已删除时为 `NULL`，不作为业务输入字段。

```sql
-- 两张配置表通用的目标字段及索引片段，非完整迁移脚本
undeletedKey TINYINT GENERATED ALWAYS AS (
  CASE WHEN deletedTime IS NULL THEN 1 ELSE NULL END
) VIRTUAL,
UNIQUE KEY uk_user_model_undeleted (userId, providerCode, undeletedKey)
```

未删除配置（含停用配置）的同一用户、模型不能重复；已删除历史可以保留多条，反复“删除 → 新增”不会互相阻塞。唯一性由数据库约束兜底，并发新增只能成功一条，另一请求提示配置已存在；新增不覆盖已有配置。该设计利用 MySQL 对[生成列索引](https://dev.mysql.com/doc/refman/8.0/en/create-table-generated-columns.html)及[唯一索引中多个 NULL 值](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)的支持。

删除及后续处理：

- 删除只写入 `deletedTime`、`updatedBy` 和 `updatedTime`，不物理删除。日常列表、按ID查看、编辑、启停、批量更新和新任务资格判断均只使用 `deletedTime IS NULL` 的记录；更新、删除操作也须带未删除条件，不能通过旧记录ID继续修改或重新启用已删除配置。
- 重复删除不改写原删除时间及最后更新信息。并发编辑与删除按实际落库结果反馈，不能把未成功更新提示为成功。
- 删除后重新新增，生成新的配置ID和创建信息，使用本次填写的 quota、启停值；旧记录保持原样。删除、重新新增及恢复不改变既定用量、扣减和重置口径，不能因更换配置ID而意外重置已消耗额度。
- 已提交任务继续按第 2 节使用原凭据关联处理，不因人员配置删除而中断查询。历史任务查询不得依赖仍存在一条未删除的人员配置。
- 误删后如需后台恢复，由授权研发核对处理：同一业务、用户、模型不存在未删除配置时才可恢复，恢复时写入本次更新人和时间；已有新配置时不覆盖新配置。业务页面保持现有删除交互，不增加恢复入口。

上线时先补充字段和约束，并完成本系统、对话生图及其他实际读写方的未删除条件适配，再切换删除入口为逻辑删除，避免旧调用方继续使用已删除配置。恢复旧版本前也必须确认其能够识别删除状态。

### 4. 改造按部门批量额度更新

将原按 appKey 更新的范围改为当前业务页面的“部门＋模型”，提交后整份覆盖命中配置的 quota。

| 项目 | 后端规则 |
|---|---|
| 输入 | 部门集合、生图模型及完整 quota 均必填；quota 按第 3 节统一校验。 |
| 部门范围 | 使用父子联动后最终勾选的实际部门集合，重叠范围去重；半选父节点本身不计入，其已选下级参与。“全公司”展开为实际部门，不作为部门ID。 |
| 命中范围 | 按执行时员工当前归属、所选部门及模型匹配当前业务的未删除配置；包含停用配置，不受列表筛选或分页限制。 |
| 更新内容 | 仅整份覆盖 quota，原对象中本次未填写的字段被移除；保留启停和人员归属，不自动新增未配置员工。实际变更同步记录更新人及时间。 |
| 无有效部门 | 不参与部门批量更新，选择全公司时也不例外；保留原配置，仍可单独维护。 |

提交时校验操作者具备当前页面使用权限，不额外按其所属部门限制。一次提交按整批成功或整批回滚实现，quota、更新人及更新时间一起生效或一起回滚；研发确认事务方案及现有能力的复用方式。

| 执行结果 | 处理规则 |
|---|---|
| 成功 | 提示更新成功，关闭抽屉并刷新列表。命中记录全部与提交值相同也属于成功，保留原更新人及更新时间。 |
| 无命中 | 按是否存在符合条件的未删除配置判断，不能用实际修改条数为零代替；提示“未命中任何记录”并保留输入。 |
| 确认执行失败 | 整批修改不生效，quota、更新人及更新时间均回滚；提示更新失败并保留输入。 |
| 结果未确认 | 超时或连接中断未取得明确结果时，提示“更新结果暂未确认，请刷新列表核对后再操作”，保留输入；不能直接认定全部成功或全部未更新。 |

前端校验通过后直接提交，处理中避免重复操作；未取得响应不代表服务端已回滚。

### 5. 完成本系统与对话生图的切换

对话生图项目目前按用户ID从本系统个人配置表读取 appKey，需与本系统同步推进部门凭据获取及任务引用改造。上线先完成对话生图的新读取方式，再切换本系统不再填写个人 appKey 的配置流程；运营表的 `idx_appKey` 随 `appKey` 字段退出一并清理。

对话生图按原读取的个人配置表所属业务切换：原读取美工个人表的链路改用美工部门表，原读取运营个人表的链路改用运营部门表，授权及额度仍读取原业务个人表。任务按第 2 节在首次对外提交前保存固定业务来源、appKeyMappingId 及 departmentIdSnapshot；后续按业务来源和映射编码查询凭据及其归属部门，实际发起部门读取快照，不合并两表匹配，也不在缺少配置时尝试另一业务。

| 阶段 | 上线内容 | 完成条件与边界 |
|---|---|---|
| 1. 部门映射及必要字段先上线 | 上线美工、运营两张部门凭据表，分别完成各业务所需部门、模型的有效映射配置及唯一 appKeyMappingId；补充任务侧 appKeyMappingId、departmentIdSnapshot 等必要字段，并按第 3 节补充逻辑删除等读写适配所需字段。 | 保留个人配置表 appKey 及原有配置流程、读取能力；两个项目未切换时仍可正常使用，不提前启用逻辑删除或退出旧字段。 |
| 2. 先对话生图，再本系统 | 对话生图先完成部门凭据获取、任务引用及未删除条件适配并验证；再同步切换本系统的新任务凭据获取和个人配置写入规则。新任务及凭据引用遵循第 2 节，历史任务按本节过渡规则处理。 | 本系统切换前，确认对话生图及其他新任务调用方已不再依赖个人 appKey；过渡期新增、删除后重新新增或恢复的配置须满足当时各调用方的新任务读取要求。双方新任务、部门归属及历史任务查询均通过验证。 |
| 3. 旧字段退出 | 确认双方生产代码均不再从用户配置表读取或写入 appKey 后，弃用该字段；满足清理条件时可直接删除。用户配置表继续承载用户授权、quota、启停等用户维度配置。 | 删除前确认历史任务和拟采用的回退方案不再依赖该字段；仍需使用的原凭据及关联已保留在可用的任务快照或其他受控记录中。关闭残留读写路径，验证两个项目均可正常运行。 |

旧字段退出以双方完成生产切换和验证为前提。弃用或删除用户配置表 appKey 时，部门映射及历史任务仍需使用的凭据继续保留。回退前须确认目标版本能读取切换后新增或重新新增的有效配置及其所需凭据；不能仅因旧字段仍在就认定可回退，删除字段后的回退版本也不能再依赖该字段。

新配置流程启用以新任务读取完成切换为前提；仍保留的历史任务查询须能取得原任务对应凭据，不依赖新建或重新新增的个人配置。历史查询及回退依赖未退出前，继续保留其所需旧字段和关联信息。

**历史任务过渡**

按本节分阶段上线时，以下新旧任务边界以各项目实际切换到部门凭据获取方式的时点为准；部门映射表单独上线不代表调用方已经切换。新旧路径须结合该项目切换边界、任务首次对外提交记录及已有状态判定，不能仅凭 appKeyMappingId 或 departmentIdSnapshot 是否为空，也不能仅凭任务创建时间判定。研发上线前确认现有信息能够可靠区分；依据不足时明确反馈异常并核对，不能自动归入历史路径。

- 本项目切换前已对外提交的任务，可在过渡期内继续按原方式查询，无需全量回填 appKeyMappingId 或 departmentIdSnapshot。无法确认历史实际部门时，departmentIdSnapshot 保持 NULL，不按用户当前部门或映射部门补造历史，也不能按当前部门映射替代原任务凭据；部门快照为空不阻断其原有结果查询。
- 本项目切换后首次对外提交的任务必须按新规则保存 appKeyMappingId 和 departmentIdSnapshot，不能因缺少必要字段或对应记录而误走历史路径；切换前创建但仍在内部排队、切换后才首次对外提交的任务同样适用。
- 历史任务结束、相关依赖清理完成前，保留查询所需的原凭据及关联信息；业务页面移除相关入口，不等于可以同时删除其他项目或历史任务仍依赖的 appKey 字段。
- 极少量历史异常允许人工处理；原配置已删除或凭据已撤销时需明确异常，不宣称一定可恢复。

本系统切换后，appKey 不出现在业务页面、页面数据、面向业务人员的接口、导出、普通日志和错误提示中，业务端旧写入入口同步关闭；其他项目服务端的过渡读取按上述阶段保留和退出。

appKeyMappingId 是普通内部标识，可按现有权限用于任务信息或日志排查，不受上述真实 appKey 的禁止输出规则限制；本期不因此新增管理页面或列表字段，也不将其作为鉴权依据或向业务端返回真实 appKey。

切换前验证所用模型和部门的凭据匹配、调岗后的新任务、已提交任务查询及现有重试处理。个人配置逻辑删除须先完成本系统、对话生图及其他实际读写方的适配，再启用删除标记；过渡与回退均须保持原任务凭据关联，回退版本须兼容删除状态。

## 验收标准

以下 A01–A51 按七类场景覆盖美工、运营两端及跨项目切换。页面交互见 HTML 原型，数据规则以对应后端章节为准；逻辑删除、唯一约束、基础留痕、批量事务、组织查询、任务凭据、计费归属、项目切换与实际生图结果需由研发实现后验证，不能以静态原型演示代替验收。

| A47 | 通过 SQL 批量初始化新配置，随后由管理员编辑其中一条 | 初始化创建人、更新人均为 system；编辑后创建人仍为 system，更新人为实际管理员用户ID字符串，更新时间正确，未改动记录的更新信息保持不变 |
